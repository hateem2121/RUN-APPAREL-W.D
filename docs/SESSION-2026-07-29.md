> ## Incident during this deploy — data loss, caught and restored
>
> The migration rebuilds the `products` table, and `DROP TABLE products`
> **cascade-deleted two array tables it was not supposed to touch**:
> `products_performance_features` (3 rows) and `products_customisation_steps`
> (4 rows). The live N001 page lost its "Performance" list and its "How we build
> your product" steps for roughly four minutes.
>
> - **Why it happened:** the cascade-on-rebuild trap *was* identified and fixed —
>   but only for the new `products_colourways` table. The same reasoning was never
>   applied to the two arrays that already existed.
> - **Why the tests missed it:** the replay harness asserted row counts for the
>   table the migration was about, and nothing else. It reported a clean run.
> - **What caught it:** diffing the public API response before and after the
>   deploy. The migration logs said success.
> - **Recovery:** restored from the pre-deploy backup
>   (`backups/d1/run-apparel-viewer-db-2026-07-29-10-19-55.sql`), with the original
>   row ids and ordering. The API is now byte-for-byte identical to the pre-deploy
>   baseline. Taking that backup first is the only reason this was a four-minute
>   problem rather than a rewrite-the-content problem.
> - **Fixed:** the migration now stages *every* child table of `products`, and the
>   replay harness fails loudly if any child table ends up empty (verified by
>   replaying the shipped version and watching it report the loss).
>
> **The rule, for next time:** before rebuilding a table, enumerate its children —
> `SELECT name FROM sqlite_master WHERE sql LIKE '%REFERENCES \`products\`%'` —
> and stage all of them. A migration that touches one table can still destroy
> another.

## Why

Two problems, one root cause: the CMS was making the owner hold facts in their head
that the computer already knew.

1. **CLO had to name colourways exactly.** `docs/FIRST-GARMENT-UPLOAD.md` told the
   owner that the colours inside CLO must read `N001-NAVY`, `N001-BLACK`,
   `N001-CRIMSON` "character for character", and called it *"the single most common
   thing that goes wrong."* A mismatch was silent until the colour buttons died on
   the live page, and the fix was a full CLO re-export plus another ~350 MB upload.

2. **One fact lived in three places.** A colour's "am I the default?" was encoded in
   `colourways.isDefault`, in `products.default_colourway_id`, and kept in step by an
   `afterChange` hook. Managing a product's colours meant navigating away from the
   product, and the three could drift into states the publish gate rejected for
   reasons that were not obvious from the screen.

Live evidence that this had already gone wrong: `N001` sits in production
`published`, `variants_verified = 1`, `glb_asset_id = NULL` — a combination the
publish gate forbids. The gate only ran on *product* save, so deleting the model
from the media library walked straight past it.

## What changed

**Colours are now an inline array on the product.** The `colourways` collection is
deleted. Row order is the answer to "which colour do people see first?", so there is
nothing left to keep in step and a colour cannot be orphaned from its product.

**CLO names are opaque handles.** The shrink robot reports the names it found inside
the file, in file order, onto the product as `fileColours`. The owner picks from
them on the Colours tab: *"Which colour in your CLO file is this?"*. The chosen
string is stored as that colour's `variantId` and handed to `<model-viewer>` as its
`variantName`.

**Nothing is renamed**, so there is no second processing pass and no extra container
cost. This fell out of the design decision to let the owner pick the file's *real*
names rather than have the pipeline rewrite them.

Three values the public API still exposes are now derived, not stored:

| Field | Now derived from |
|---|---|
| `sequence` | position among the colours actually on show |
| `isDefault` | the first switched-on row |
| `variantsVerified` | every switched-on colour points at a name that is really in the file |

**Editor navigation is three items:** Products · Photos & 3D files · Settings.
`raw-uploads`, `events` and `users` are hidden from non-admins; uploads are reached
through the product's **3D file** tab (a `join` field), so the editor never leaves
the product.

## Bugs found and fixed along the way

Four were only findable by *running* things, not by reading them.

1. **The generated migration would have failed in production.** `migrate:create`
   emitted the brand-new `file_colours` column inside the `SELECT` from the *old*
   `products` table → `no such column: "file_colours"`, aborting the migration
   *after* `colourways` had already been dropped.

2. **`PRAGMA foreign_keys=OFF` is a no-op on D1.** SQLite ignores it inside a
   transaction and D1 wraps statements in one; Cloudflare's docs specify
   `PRAGMA defer_foreign_keys` instead. The real fix was statement *order*:
   `products` and `colourways` reference each other, so neither could be dropped
   first. The child is emptied before the parent rebuild and dropped only once
   nothing refers to it.

3. **The table rebuild cascade-deleted the backfill.** Drizzle rebuilds a table as
   create-new → copy → `DROP TABLE old` → rename, and `products_colourways._parent_id`
   cascades. Copying colours in before that DROP produced a migration that
   "succeeded" and left every product with zero colours. They are now staged in a
   table with no foreign keys and copied in after the rebuild.

4. **Publish-gate errors surfaced as "Something went wrong."** A plain `Error`
   thrown from a Payload hook is swallowed by the generic handler — the exact
   failure mode `FIRST-GARMENT-UPLOAD.md` tells the owner to report as a bug. The
   hook now rethrows as `APIError(message, 400)`; `assertPublishable` stays free of
   any Payload import so it remains testable without a database.

Also closed: **deleting a media file used by a published product is now blocked**
with a message naming the products. That is the hole that left N001 live with an
empty 3D stage.

## How it was verified

- **Public API contract held.** `GET /api/public/viewer/n001/navy` captured from
  production *before* any change, compared path-by-path against the rebuilt schema.
  Every key present in both has **identical values**. The only two differences are
  `product.glbUrl` and `product.posterFallback` — null in production purely because
  N001's model was deleted. `projectViewer.test.ts` (the contract test) passes with
  **zero edits**, not even to its setup.
- **Migration replayed against real data** with `PRAGMA foreign_keys = ON` against a
  `VACUUM INTO` snapshot, plus an adversarial second product whose default was not
  first in tab order. Up and down both clean, no FK violations, ids and order
  preserved exactly.
- **All 5 migrations applied to a fresh D1** through Payload itself.
- **Viewer end-to-end**: model loads, `availableVariants` matches the CMS,
  clicking a colour changes both URL and GLB variant, retired colours vanish and
  renumber, a retired QR falls back to the top switched-on colour, mobile has no
  horizontal overflow.
- **Every validation message triggered deliberately** and checked for wording.
- 177 tests, typecheck clean across all five workspaces.

## Payload v4 readiness (audited today)

`latest` is 3.86.0 — what this repo pins. v4 exists only as `4.0.0-canary.18`.
Applied now, because all are no-ops on 3.86:

- `versions: false` on every collection and global — v4 flips the default to ON,
  which would add six `_versions` tables to D1 and roughly double row-writes.
- `apps/cms` TypeScript 5.9.3 → **6.0.3** (v4's stated minimum). Deliberately *not*
  7.x: Next.js 16 rejects it — *"TypeScript 7.0.2 does not provide the compiler API
  required by Next.js"*.
- Both `r2Storage()` calls kept adjacent so the v4 `plugins` → `storage` move is a
  three-line diff. That key does not exist in 3.86, so it cannot be done early.
- Chose `array` over `blocks` for colours; avoided `forceSelect`, `blockReferences`
  and `min`/`max` on upload fields — all removed in v4.

**Still to do before any v4 upgrade:** re-save `robot@wear-run.help` to regenerate
its API key (v4 drops the sha1 HMAC fallback, so pre-3.46.0 keys stop
authenticating and the auto-shrink flow dies silently), and re-test the
`@payloadcms/storage-r2` patch against v4's shared upload-instructions endpoint.

## One behaviour change worth knowing

`push: false` is now set on the D1 adapter. Drizzle's dev auto-push was silently
competing with the committed migrations for source-of-truth, and it does not run
their data backfills — `pnpm migrate` opened with *"You're about to delete
colourways table with 3 items"* instead of applying the migration that **moves**
those three rows. Schema changes now require `pnpm migrate:create`.

## Before you push

Pushing `main` triggers CI, which applies migrations to the **live** D1 before
deploying. So:

1. Back up production D1 (`docs/BACKUP-RESTORE.md`).
2. Capture `curl https://cms.wear-run.help/api/public/viewer/n001/navy` for a
   before/after diff.
3. Push. Watch the `migrate` job for
   `inline_colourways: moved 3 colour(s) onto their products.`
4. Re-run the curl and diff. Only `glbUrl`/`posterFallback` should differ, and only
   if N001 is still without a model.

**N001 itself is untouched, by decision.** It is still published with no 3D file, so
a QR scan shows the correct page with an empty 3D area. Attaching a real garment
file fixes it; that is the outstanding piece and always was.
