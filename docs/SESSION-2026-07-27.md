# Session log — 2026-07-27: why raw uploads never worked

A single session's worth of debugging on one symptom ("the upload failed") that
turned out to be **four independent defects**, one of which meant the raw-upload
inbox had never functioned since it was written. Recorded because most of it is
non-obvious and expensive to re-derive.

## Timeline of what was wrong

### 1. `mimeTypes` broke every upload over 50 MB — fixed (`a45aea9`)

`@payloadcms/storage-r2/dist/getFile.js` deliberately returns an **empty body**
when `fileSize > 50MB && clientUploadContext` ("or the Worker will run out of
memory"). Payload's `addDataAndFileToRequest` builds `req.file.data` from that →
0 bytes. `checkFileRestrictions` runs **only when `upload.mimeTypes` is set**;
`fileTypeFromBuffer(empty)` → `undefined` → falls back to `getFileTypeFallback()`
whose `extensionMap` has no `glb` → guesses `text/plain` → `ValidationError`.

`file-type` *does* recognise GLB, which is why <50 MB always worked.

Fix: drop `mimeTypes` from `RawUploads` (empty list makes `validateMimeType`
short-circuit to `true` and stops the field validator being attached at all) plus
`allowRestrictedFileTypes: true`. `checkRawUpload()` in `rawRules.ts` was always
the real gate. Guarded by `apps/cms/src/collections/uploadConfig.test.ts`.

Separately: `@payloadcms/ui` joins `mimeTypes` verbatim into the file input's
`accept`, and macOS has no UTI for `model/gltf-binary` — so `.glb` was greyed out
in the picker. Fixed by adding the literal `'.glb'` to Media's array (inert for
validation, `validateMimeType` compares with `startsWith`).

### 2. THE root cause — storage-r2 multipart URL bug — patched (`a025b06`)

`R2ClientUploadHandler.js` computes the endpoint **once, as a string**:

```js
const endpoint = `${baseURL}?${String(new URLSearchParams(params))}`
```

then mutates `params.multipartId` / `multipartKey` / `multipartNumber` and
re-fetches that same frozen string. The mutations never reach the URL.

Consequence: **every chunk POST hits the init endpoint.** The server takes the
`else` branch in `getHandleMultiPartUpload` and calls `createMultipartUpload()`
again instead of `uploadPart()`. No part is ever uploaded, the upload is never
completed, **nothing is written to R2**. The `complete` call is lost identically,
and its init-JSON response is read as `await complete.text()` and returned as the
object key.

**Evidence** — `wrangler tail` during a live 382 MB upload: **66 requests to
`/api/storage-r2-multi-part-upload`, zero carrying `multipartId`.**

Fixed by extending `patches/@payloadcms__storage-r2@3.86.0.patch` to rebuild the
URL per call. **Upstream bug — report it and drop the patch when fixed.**

### 3. A missing file still creates a document — guarded (`6fac752`)

`addDataAndFileToRequest` treats a **404 from the storage static handler as
success**: the response is truthy, so `req.file.data` becomes an empty buffer and
the create proceeds on client-supplied metadata. That is why a failed upload
produced a record with a correct-looking name and size pointing at nothing, and
no error until the shrink job failed minutes later with
`Could not read raw object ... (404)`.

Guard added in `RawUploads.beforeChange`: HEAD the ingest bucket for the key
before allowing the create.

### 4. Hook errors must be `APIError` — fixed (`fd0ecc6`)

That guard first threw a plain `new Error()`. Payload's generic handler swallows
those into **"Something went wrong."**, so its first live test told the operator
nothing. **Any user-facing failure thrown from a Payload hook must be
`APIError(message, status)`** — Payload surfaces that verbatim.

## Also fixed this session

- **`--simplify` was tearing printed logos apart** (`d861257`). It ran with
  `error: 0.001` — 10× the glTF-Transform default — and no `lockBorder`. `ratio`
  is only a target; a loose error budget lets the simplifier distort heavily to
  reach it, and smearing UVs under a printed graphic tears the artwork.
  Measured on a real 373 MB export at `--simplify 0.05 --meshopt`:
  | settings | size | triangles |
  |---|---|---|
  | old (no lockBorder, error 0.001) | 14.2 MB | 850k — logos torn |
  | lockBorder only | 36.1 MB | ~2.4M |
  | lockBorder + error 0.0001 | 58.3 MB | 6.0M — over the 40 MB cap |
  Textures were **2.1 MB in every case** — this was always geometry, never
  texture resolution.
- **First-ever successful shrink-container deploy** (2026-07-27 12:54Z, image
  `sha256:615824fc` replacing the 2026-07-24 `sha256:88aaca34`). CI had failed
  3/3. See the manual-redeploy requirements in `RAW-UPLOAD-PIPELINE.md`.
- Dependency bumps to latest, `engines.node` `>=20` → `>=24` (Node 20 is EOL).

## Method lessons

**A local reproduction that passes can be worthless.** The 382 MB file was
reproduced end-to-end against a local CMS and *succeeded* — because the repro
script rebuilt the URL correctly per request, i.e. it tested the intended
behaviour rather than the shipped library's. That sent the investigation down a
long wrong path. Reproduce against the **real client**, or read the real client's
source, or watch production traffic.

**`wrangler tail` is the tool that cracked it.** Static reading of Payload's
source repeatedly "proved" the code was correct. Only live request logs showed
the truth. Note tail is **live-only** — there is no historical query, so arm it
*before* asking for a retry. A CMS redeploy kills an attached tail session.

**Don't trust CI logs for "is X deployed?"** — query the platform. The shrink
pipeline was documented as never-deployed based on CI failures; it had in fact
been deployed by hand and was healthy.
