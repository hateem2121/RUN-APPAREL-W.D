## 0. THE ACTUAL DEFECT — opaque layer z-fighting. ✅ RESOLVED (section 7)

⚠️ **TWO CLAIMS BELOW WERE CORRECTED BY MEASUREMENT — see section 7.** It is **2
garments, not 16** (that table is the bias-everything screen measurement it warns you
about, and `t003` IS Minecut Motion), and the fix is neither name-based nor
bias-everything.

**What the owner sees:** small white specks scattered over the cloth, appearing and
disappearing as the garment turns. They called it "sparkling", "glitching", and "bits
vanish and come back". They circled it in a screenshot. It is one defect.

**The mechanism, proven.** A garment panel has TWO opaque surfaces in almost the same
place: the printed layer (e.g. `Material_Graphic`) and a plain fabric layer behind it.
Hiding the printed layer on Minecut Motion turned the skirt **100% white**, exposing
the layer underneath. The two sit at near-identical depth, so the GPU picks a different
winner per pixel and per frame, and the pale layer beneath punches through.

**It is NOT in any texture.** Every base-colour image in Minecut was measured: none has
light flecks on a dark field. The specks are produced at render time.

**⚠️ THE SHIPPED DEPTH BIAS CANNOT REACH IT, BY DESIGN.** `applyDecalDepthBias` skips
anything that is not `alphaTest > 0` — i.e. only cut-outs are biased — with the comment
that biasing the garment body would push it through what is behind it. That reasoning
is right for the BODY and wrong for a printed layer sitting ON the body. It is why p001
was repaired and Minecut was not.

**The same lever fixes it.** Biasing `Material_Graphic` on Minecut:

| bias | white specks on the skirt |
| --- | --- |
| none (as shipped) | 5.196% |
| -1 | 1.586% |
| -4 | 0.173% |
| **-8** | **0.002%** |
| -16 | 0.000% |

**Scope: 16 of 16 garments.** Percentage of the garment that changes when every OPAQUE
material is biased -8, at a fixed camera:

| garment | affected | garment | affected |
| --- | --- | --- | --- |
| **p001** | **17.625%** | TERRA | 2.235% |
| KINETIC | 8.756% | s001 | 1.434% |
| d001 | 8.086% | t002 | 1.260% |
| t003 | 7.418% | ARISAN | 1.056% |
| MINECUT | 5.179% | b001 | 0.951% |
| CAPSULE | 3.764% | v001 | 0.771% |
| n001 | 2.517% | s002 | 0.698% |
| | | POLO | 0.670% |
| | | d002 | 0.372% |

**p001 is the WORST at 17.6%** — the garment this session "fixed". The decal bias
repaired its cut-outs and never touched this.

⚠️ **That 16-garment number is a SCREEN measurement, not a defect count.** It biases
every opaque material, so some of the change may be legitimate (silhouettes, panels
that genuinely should lose). It says "there is an opaque depth fight here", not "all of
that is the bug". Confirm per garment against a render before quoting it.

### The open design question

The fix cannot simply be "bias every opaque material". The existing comment is right
that the garment BODY must not be pulled forward. So the next session needs a sound way
to tell **a printed layer sitting on cloth** from **the cloth itself**.

- **Name matching (`Material_Graphic`) is the quick way and this repo has been burned by
  it** — a CLO export leaves textures anonymous, and a name-based artwork check was
  already found silently inert once.
- **Geometric is sound**: a surface sitting a hair in front of another IS a decal
  whatever its material says. This repo already measures those gaps — that is how
  p001's 0.001 mm and n001's 0.169 mm are known.
- The pipeline can compute adjacency; `model-viewer` at runtime cannot.

## 1. What was fixed

### The decal depth bias was EIGHT TIMES too weak — `fix a1ea5fc`

`OFFSET_FACTOR/UNITS` shipped at `-1/-1`. The mechanism was right; the number was not.

| garment | pixels still wrong at `-1` | at `-8` |
| --- | --- | --- |
| p001 (joggers) | 1.647% | clean |
| d001 | 0.793% | clean |
| n001 (source of the LIVE product) | 0.000% | 0.000% |

Rendered evidence, not inference: at `-1` p001's chevrons and its "NEVER LOOK BACK"
are eaten through with holes and d001's navy chevron has a white gash torn across it;
at `-8` both are solid. Damage is still visible at `-4`. `-8` through `-128` are
indistinguishable, so `-8` is the START OF A PLATEAU rather than a value balanced on
an edge — which is why it is `-8` and not the `-4` that also nearly works.

**The old comment was wrong in both halves.** It claimed `-1` was "the smallest bias
that reliably separates two coplanar surfaces" (false — `-1` leaves p001 destroyed)
and that larger values bleed a far-side decal through to the front. The second is a
REAL failure mode but its threshold was out by two orders of magnitude:

| bias | n001 (tightest cloth in the catalogue, and LIVE) |
| --- | --- |
| `-8` | 0.000% of pixels change |
| `-64` | 0.000% |
| `-512` | 0.009% |
| `-4096` | 0.168% |

So `-8` carries at least a 64× margin. **That 0.000% is also the safety argument for
production: this value cannot alter the garment already published.**

On the garments `-8` does change, the change SATURATES at `-8` and does not grow
through `-4096` — that is damage being repaired, not a decal bleeding through.

**Why no test caught it.** Every assertion checked that a bias was APPLIED; none
checked it was STRONG ENOUGH. That is this repository's recurring shape — a fixture
that cannot exhibit the defect it guards. `decal-depth-bias.test.ts` now enforces an
8..64 band with the measurement named, and BOTH negative controls were verified:
reverting to `-1` fails the floor; `+512` fails the ceiling and the sign.

### A revert silently un-fixed the pipeline — `fix 41eab21`

The `-8` change to `review-server.ts` had been swept into the *second* commit by a
`git add -A`, so reverting that commit reverted it too. The review viewer would then
have shown p001 shattered while the product rendered it solid — the exact
misrepresentation the drift test exists for. **The test caught it, not a later look at
the screen.** Stage per package when two copies must agree.

## 2. What was found, proven, and deliberately NOT fixed

### The printed artwork is painted the cloth's own colour — OPEN

glTF renders a material as base-colour **TEXTURE × base-colour FACTOR**. The artwork
textures in this catalogue are near-white stencils (measured ink `rgb(230..255)`), so
the FACTOR decides the ink colour. CLO writes the colourway's **fabric** colour into
that factor on artwork materials.

| garment | texture ink | × factor | = rendered |
| --- | --- | --- | --- |
| p001 (healthy) | rgb(255,255,255) | `[1.00 1.00 1.00]` | rgb(255,255,255) |
| KINETIC | rgb(246,246,246) | `[0.65]` | rgb(159,159,159) |
| Minecut Motion | rgb(246,246,246) | `[0.13]` | rgb(33,33,33) |

**Scope: 13 of 16 processed garments**, several at factor `0.00` — the print
multiplied to nothing. `n001`, the source of the live product, is one of them. Clean:
p001, s001, and TERRA ACTIVE ZIP (which has no cut-outs at all).

**It is in the RAW CLO exports, byte-identical to our output.** We did not cause it.
`tools/asset-pipeline` writes `setBaseColorFactor` only in `placeholders.ts`, never in
the real processing path.

**It is NOT the flicker and the depth bias cannot touch it** — toggling the bias
between 0 and `-8` changes **0.000%** of those pixels. The two were read as one defect
because both end in "the print is not there". That is how the first fix came to be
called complete while the owner could still see the problem.

**Two corrections were tried and BOTH are wrong.**

1. *Force every cut-out white.* Turns d001's dark olive graphic white — **23.1% of its
   pixels**. A white stencil × a dark factor is exactly how a COLOURED print is
   authored, so a blanket rule destroys legitimate design.
2. *Whiten only a print whose factor matches a cloth colour.* Shipped as `0cf4fea`,
   then **reverted as `447d15f`**. Minecut's white colourway has a dark grey skirt AND
   a white waistband; its slogan sits on the white band, correctly dark and readable —
   but matches the grey skirt, so the rule painted it white-on-white. It introduced
   the defect it was written to remove, on a colourway that did not have it.
   Narrowing to the DOMINANT cloth colour fails differently: it picks KINETIC's black
   trim over its fabric and corrects nothing there.

**Why it belongs in the pipeline.** The question is whether a print matches the cloth
**it sits on**. `model-viewer`'s material list carries no adjacency; this package can
see which panel a decal overlays. Nothing from `0cf4fea` should be re-applied in the
viewer without that.

**Owner's ruling, 2026-08-28:** *"Prints should stay subtle — find the REAL problem."*
Recorded as their decision. Note the tension worth revisiting: they also reported
"graphics **visibility** issues" on exactly the garments with the worst tint, so it is
not certain both statements refer to the same thing.

## 3. Hypotheses TESTED AND DISCARDED — do not re-chase

Recorded because each cost real time and each looked convincing.

| hypothesis | how it died |
| --- | --- |
| `alphaToCoverage` for cut-out edges | No effect; slightly worse (KINETIC 4.22→4.42%, b001 3.09→4.60%). model-viewer provides no MSAA target. |
| Texture anisotropy 4 → 16 | No change at all (4.22% → 4.22%). |
| Texture minification (3947px art on a ~300px garment) | Zooming in did not reduce it (KINETIC 4.22% → 4.21%). |
| Alpha-cutoff mipmap "vanishing" | Ink coverage is FLAT across five zoom levels and three cutoffs (0.5/0.3/0.15). The print is not being erased. |
| Topstitch geometry | Compelling correlation — 76–98% of geometry on every garment reported bad, 0–3% on the clean ones — that does NOT hold: hiding it removes only **8–15%** of the aliasing error. |

### A detector that measured the wrong thing

A "flip rate" test (two frames 0.05° apart) ranked KINETIC 4.22%, t003 3.45%, b001
3.09% and matched the owner's list. **It was confounded.** A 0.05° rotation shifts
every edge by roughly half a pixel, so it largely measured EDGE DENSITY — and a
splatter print is nearly all edge. Its noise floor was a clean 0.000%, which made a
confounded metric look trustworthy. Ranking withdrawn.

A movement-independent replacement (diff against a 3× supersampled render) is sound
and left **b001 as a genuine outlier at 8.79 mean error / 8.24% badly-aliased pixels**,
against 1.4–2.9 for everything else. The owner did not report b001. Unexplained.

## 4. Measurement traps — four instruments reported success while measuring nothing

- **`getCameraOrbit()` returns the CURRENT EASED position, not the goal.** Even after
  `setAttribute('camera-orbit', …)` + `await updateComplete`, the camera is still
  animating, so two different requests compare as identical frames. Call
  **`jumpCameraToGoal()`**, wait two rAFs, then read it back. This is a SECOND trap on
  top of the documented one (`mv.cameraOrbit = …` being ignored).
- **Writing `backing.color` directly changes nothing on screen.** Reported 10
  materials corrected and moved **0.000%** of the pixels across six garments. Use
  `material.pbrMetallicRoughness.setBaseColorFactor(...)` — public API, and it repaints.
- **`getAlphaCutoff()` THROWS on a lazy variant material** — it calls
  `ensureMaterialIsLoaded` internally. Guard with the public `isLoaded`, as the depth
  bias already does.
- **`page.evaluate(() => …)` throws `ReferenceError: __name is not defined` under
  `tsx`** — esbuild injects a name-preservation helper into the function that runs in
  the BROWSER. Pass the code as a STRING.
- **A visible status line may be from a LATER pass than the one that acted.** The ink
  correction ran on `load`; the `variant-applied` pass then found nothing left to do
  and reported zero. That nearly hid a regression. A/B by serving the same page twice
  with `page.route` rewriting one line, so the repair is the only difference.
- **Headless Chromium renders with SwiftShader, not a GPU.** Measured:
  `ANGLE (Google, Vulkan, SwiftShader)` headless vs `ANGLE (Apple, Metal, M4 Pro)` in
  the Browser pane. A shimmer the owner sees may simply not reproduce headless.
- **Positive control that works:** `@gltf-transform` refuses a Meshopt file until the
  decoder is registered. Reuse `createIO()` from `tools/asset-pipeline/src/io.ts`
  rather than a fresh `NodeIO`, or every garment reads as "UNREADABLE".
- **Read variants off the PRIMITIVES.** `root.getExtension('KHR_materials_variants')`
  returns nothing and reads as "this file declares no colourways" — false for all 16.

## 7. RESOLVED — the geometric overlay detector (appended 2026-08-28, later)

Section 0's open design question was: **how do you safely tell a printed layer sitting
on cloth from the cloth itself?**

### The answer: ask which one is in FRONT

A printed layer and the cloth beneath it are both OPAQUE, both in a stack, both ~0.1 mm
apart. The only thing separating them is which one is in front — and that is a fact
about the geometry, which the pipeline can measure and `model-viewer` cannot.

`tools/asset-pipeline/src/overlay-depth.ts` casts a short ray both ways along each
surface normal from area-weighted samples, and computes:

```
layeredFraction = share of the surface with an aligned neighbour within 0.30 mm
frontness       = back / (back + front)
gapMm, alignment
gate: layered >= 0.30 && frontness >= 0.75 && gapMm <= 0.30 && alignment >= 0.98
```

⚠️ **`frontness` is a RATIO and that is the whole trick.** The obvious measure — "what
share of this surface has something behind it" — is badly conditioned, because CLO
writes a printed layer as DOUBLE-SIDED geometry: Minecut's graphic has exactly **2.00x**
the fabric's area, half of it facing inward, so only **48%** of its samples can ever
find support. Dividing by the stacked share turns that 48% into **0.964**.

Measured over all 16 processed GLBs, OPAQUE primitives:

| surface | frontness | verdict |
| --- | --- | --- |
| Minecut/t003 `Material_Graphic` | **0.964** | overlay |
| KINETIC `2Sublimated Sports Bra` | **0.825** | overlay |
| Minecut `Default Fabric` (the cloth) | 0.026 | rejected — UNDERNEATH |
| KINETIC `cotton_ponteroma` (the cloth) | 0.061 | rejected — UNDERNEATH |
| **p001 `Fleece_Terry` (BODY PANEL)** | **0.340** | **rejected** |
| topstitch / zipper hardware | — | rejected on alignment 0.93-0.97 |

p001 is the garment section 0 lists worst on the bias-everything screen test, and its
body panels are rejected. That is the constraint holding.

### Scope: 2 garments, not 16

Only **Minecut Motion** and **KINETIC SPLATTER SPORTS BRA** carry an OPAQUE stacked
layer — the two the owner named. `t003.glb` **IS** Minecut Motion (same 49 primitives,
same material IDs `330347`/`330411`/`330439`/`330501`), processed twice, so there are 15
distinct garments in the 16 files. Section 0's 16-garment table is the screen
measurement it warns about, not a defect count.

### The decision is written into the asset, and the BIN chunk is untouched

The pipeline writes `extras.depthBias` on the material; three.js copies glTF material
`extras` to `Material.userData` (`assignExtrasToUserData`) and `Material.copy`
deep-clones it, so it survives model-viewer's own cloning. Verified in a real browser
with the un-annotated file as the negative control: **0 materials carried the record
before annotation, 1 after**, at `alphaTest: 0`.

⚠️ **The GLB is patched JSON-chunk-only.** Re-serialising through `@gltf-transform`
would re-encode meshopt and re-quantize every vertex — the "never run the pipeline on
its own output" trap. `extras` lives entirely in the JSON chunk and adding a material
never moves a bufferView, so **13 of 16 files come out byte-identical**, n001 and p001
among them, and the three that change are verified BIN-identical per file.

⚠️ **All five colourway materials are flagged, not just the base.** Minecut's graphic
resolves to materials #3/#19/#32/#45/#58. Flagging one would repair one colourway of
five — the exact shape of the decal fix that reached 6 of 26 decals.

### Rendered evidence

Fixed camera, verified by reading `getCameraOrbit()` back after `jumpCameraToGoal()`.
Headless Chromium, **SwiftShader** (`ANGLE (Google, Vulkan … SwiftShader)`), 900x900 at
DPR 2. Speck metric is single-frame local contrast, so it cannot be confounded by edge
density the way the withdrawn two-frame rotation metric was.

| garment | view | specks before | specks after | pixels changed |
| --- | --- | --- | --- | --- |
| Minecut Motion | skirt-front | 0.228% | **0.018%** | 2.822% |
| Minecut Motion | skirt-side | 0.243% | **0.019%** | 2.798% |
| KINETIC SPLATTER | front | 0.205% | **0.048%** | 2.081% |
| **n001** (source of LIVE) | front | 0.013% | 0.013% | **0.000%** |
| **p001** | front | 0.090% | 0.090% | **0.000%** |

The difference map is almost entirely "a bright pixel got darker" — specks closing, not
artwork being removed — and the fabric's own pattern survives in the after render.

### Negative controls, verified by breaking the code on purpose

Lowering the band floor to `-1` fails 2 tests; biasing every opaque material fails 7.
Both pass again when restored. A test that only checks "a bias was applied" is what let
the previous defect ship.

## 8. `eval:artwork` — the handover was wrong on all three counts

The 2026-08-27 handover recorded this as *deterministic, pre-existing, and green in CI*.
Measured 2026-08-28:

| where | fidelity / balanced / CONTROL | result |
| --- | --- | --- |
| `origin/main`, this machine, same node_modules | 1.650 / 3.070 / 9.370 | **passes** |
| this branch, this machine | 15.290 / 16.070 / 18.760 | fails |
| this branch, CI's own container `mcr.microsoft.com/playwright:v1.62.1-noble` | 15.300 / 16.080 / 18.770 | **fails** |

- **Not green in CI** — CI had never run this branch. The green run cited was `main`.
- **Not pre-existing** — `main` passes on this machine.
- **Not an environment difference** — CI's own container reproduces it to within 0.01.

**Cause.** `normalizePbr` joined `optimizeGlb` on this branch and runs on the optimized
side only, while the eval's baseline is the raw fixture — breaking the eval's own stated
promise that "the only variable is the decimation". All three rows moved TOGETHER,
control included, which is the signature of a constant offset rather than damage.

**Checked before fixing, because the whole point of this eval is that the blocking gates
cannot see artwork damage.** `sheet-balanced` shows the letterforms INTACT — same
strokes, no holes, no smearing — and merely lighter, which is what a wrongly-metallic
surface looks like once corrected. `sheet-control` from the same run shows real damage
for comparison: letters torn into shards.

**Fixed in the eval, not the pipeline**: the fixture is PBR-normalised before the
baseline render. Restores 1.680 / 3.100 / 9.390 — and a *lower* mean error than `main`
(1.0 vs 1.52), because the two sides now differ only geometrically. The negative control
still trips at 3.0x the shipped preset.

⚠️ The trap is the `opaque`-default trap one module along: `normalizePbr` defaults ON
inside `optimizeGlb` and has no equivalent on a hand-built baseline. Warned at the call
site in `optimize.ts`, which is where the next person will add the next pass.
