## Found 2026-08-27, while fixing the see-through and metallic defects

**SIX of the 28 raw exports CANNOT BE READ AT ALL** — ARISAN SPORTS BRA, CAPSULE
CORE HOODIE, KINETIC SPLATTER SPORTS BRA, Minecut Motion, STRUCTURE POLO SET,
TERRA ACTIVE ZIP. Each carries ONE texture entry with no `source`, so
gltf-transform's reader creates `null` and dies on `Cannot read properties of null
(reading 'setMagFilter')` in 0.5s, before any work happens. The message names no
garment and no texture. Detectable from the JSON chunk in about a second; do not
read it as a pipeline bug.

**`createTransform` is exported from `@gltf-transform/functions`, NOT from
`@gltf-transform/core`.** Eight tests failed on that before a line of logic ran.

**COMPARE THE ARTIFACTS, NOT A PICTURE OF THE DIFFERENCE.** A rendered diff shows
what CHANGED, never whether it got WORSE. A macro crop "proved" that reduced texture
settings had damaged a slogan; it had not. `pipeline textures` settled it in one
line — the artwork was byte-identical at both settings (3169x476, 29.3 KB) and only
the fabric atlas had shrunk. The letterforms showed up in the diff because the CLOTH
around each stroke changed and outlined them. That misreading cost an hour and two
wrong conclusions.

**Artwork is separated from fabric by UV SPAN, not by name** (`artwork-geometry.ts`).
Measured over every textured primitive in all 28 exports: fabric median **294.81**,
topstitch 0.83, artwork **1.00**. Names cannot do it — real artwork materials are
called `ZZ00000ZZZZ0`, `ZZZ00000`, `76197`, `01`, `Untitled-1` and `ルン ろご。`
(Japanese for "run logo"), and 8 garments match none of the nine English words.

## Found 2026-08-27, the second half of the same session

**SIX EXPORTS ARE NOW READABLE, and the fix is narrower than "strip the dead
entry".** The one source-less texture in each is **NOT an orphan** — it is
referenced by 1 material on STRUCTURE POLO SET and 50 on CAPSULE CORE HOODIE. What
makes removal safe is measured and specific: in all six the only slot it ever fills
is `metallicRoughnessTexture`, never `baseColorTexture`, and **every** material
using it already declares `metallicFactor: 0`. So the render is unchanged by
construction. `repair-dead-textures.ts` removes the **references, never the entries**
— deleting `textures[5]` renumbers every later index and a material pointing at 6
silently acquires the picture from 7 — and pads the JSON chunk back to its original
byte length with spaces so the BIN chunk cannot move. Material counts after repair
match this file's own baseline exactly: 168/101/83/128/32/141.

**⛔ THE KHRONOS glTF-VALIDATOR DOES NOT CATCH THAT DEFECT.** Measured on ARISAN:
**0 errors, 0 warnings**. `texture.source` is OPTIONAL per the spec, so a
source-less texture is valid glTF and gltf-transform is merely stricter. Anyone
adding the validator to name that failure will find it silent. It was kept for a
different reason and earned it immediately — see below.

**EVERY PROCESSED GARMENT WAS INVALID glTF, and had been for as long as the WebP
pass existed.** The pass wrote `image/webp` without declaring `EXT_texture_webp`,
and a non-core mime-type is illegal without it: p001 **44** errors, geovent 45,
n001 42, arisan 38 — `IMAGE_NON_ENABLED_MIME_TYPE` + `TEXTURE_INVALID_IMAGE_MIME_TYPE`
in pairs. **`<model-viewer>` sniffs the bytes and renders anyway**, which is exactly
why every gate here stayed green while a stricter runtime was entitled to refuse the
textures. Declared in `texture-artwork.ts` now, pinned by a negative-control test
that strips it back out.

**`prune()` RENUMBERS UV SETS AND UPDATES ONLY THE DEFAULT MATERIAL.** Anything
reachable solely through `KHR_materials_variants` keeps sampling a `TEXCOORD_n`
that no longer exists, so the arriving colourway is correct and every other one
draws its artwork with absent coordinates. `variant-texcoord.ts` repoints them
immediately after prune. **LATENT** — measured across all 28 raw exports, *not one
material samples a texCoord other than 0*, so no real garment reaches it today; it
surfaced only because `placeholders.ts` deliberately puts artwork on a second UV
set. **Keep that fixture detail**, it is the only thing exercising the path.
⚠️ This is the SECOND time in one day that variant-only materials were skipped by a
pass that handles the eager one correctly — the other was the viewer's decal depth
bias, at 6 of 26 decals. **When a pass touches materials, ask what it does with the
ones behind a variant.**

**The spec check is a PRODUCTION dependency and is NOT inside `describeGlb`.** Both
were got wrong first. `apps/shrink/container` imports `inspectGlb` and `describeGlb`
and installs with `npm ci --omit=dev`, so a devDependency resolves locally and is
missing in the Container — green everywhere, failing at runtime as a broken shrink
job. And resident memory runs **~3.4x the file size** (42 MB → 234 MB RSS; 573 MB →
**1,955 MB**), while `describeGlb` is called on the RAW upload and reads only the
JSON chunk so the 1.25 GB Cycling Bib costs what the 5 MB PRO-PILE costs. Putting it
there would OOM a container that already peaks at 5.27 GB. `SPEC_MAX_BYTES` is
768 MB and the two exports over it are **skipped by name** — a skip must never read
as a pass.

⚠️ **`pnpm eval:artwork` FAILS ON macOS AND PASSES IN CI, and this file used to
claim it could not.** The old wording: *"the CI numbers match a developer Mac to
three decimal places, because the eval diffs two renders from the same browser in
the same run, so the rasteriser cancels."* Measured 2026-08-27 — local
**15.290 / 16.070 / 18.760** against a 5.000% ceiling, **byte-identical at three
different commits** including `521af2c` before any of that session's work, on the
same **Playwright 1.62.1** CI pins. CI's `artwork` job is green on `main`. So the
eval is perfectly deterministic and the rasteriser does **not** cancel across
platforms; CI runs it inside `mcr.microsoft.com/playwright:v1.62.1-noble` and that
Linux Skia is the calibration. **Do not raise the ceiling to make a Mac green**, and
do not read a local failure as a regression — reproduce it in the container, or
trust CI. The three numbers being nearly equal (fidelity barely better than the
damage control) is the tell that the measurement is platform-dominated rather than
decimation-dominated.
