## 3. The fix is now locked

Suite **340 → 352**.

- `src/__fixtures__/wordmark-alpha.png` is the **real** Slogan alpha channel from
  the 364 MB raw export. 13 KB, because only alpha is kept and RGB is flattened.
  Round-trip verified **exact**. Taken from the RAW export deliberately:
  `solidifyMaterials` (`optimize.ts:300`) runs BEFORE texture compression (line
  305), so `profileAlpha` never sees the WebP. It replaces a synthetic

## 4. ⚠ The gates do not catch decimation damage

Six runs from the raw export, varying `--simplify-error` from 0.0002 to 0.005.
**Every run passed all three blocking gates** — including the one set up to fail.

| run | `--simplify-error` | size | gates | wordmark, rendered |
|---|---|---|---|---|
| B | 0.0002 (fidelity) | 58.63 MB | PASS | — |
| A | 0.0005 (**balanced, live**) | 37.72 MB | PASS | **crisp** |
| **C** | **0.001** | **26.96 MB** | PASS | **fully legible** |
| E | 0.002 (**small, shipped**) | 18.81 MB | PASS | **MILE breaking up** |
| F | 0.005 | 12.14 MB | PASS | **destroyed** |

Evidence: `images/2026-08-05-size-vs-wordmark.png`.

The gates test `alphaMode`, a *settings-independent* property — which is why they
caught the 2026-08-04 bug and say nothing here. With `--uv-weight` set the UVs are
inside the error budget, so `artworkAtRisk` cannot fire; the budget was simply too
loose. **This is the repo's recurring hole one level up: in July the fixture could
not exhibit the failure; now the gate cannot.**

Also corrected during the sweep: **`--simplify` is not the aggression dial.** The
simplifier stops early once the budget binds, so the originally-specified sweep
over the ratio would have produced near-identical files and read as "nothing
helps". `lockBorder` no longer exists either.

### Consequence: `small` was deleted

Run E *is* "Smallest file" as an owner would pick it, and it damages the wordmark
while passing every check. Removed from the type, the flags, the dropdown and
every document. Old rows carrying `'small'` fall through to balanced, which is
strictly safer than what they asked for. A new test fails if any level looser than
balanced is ever added.

**`nextDetailAdvice` no longer points anywhere.** There is no smaller level to
send an oversized garment to, so it says plainly that the CLO export needs a
lighter mesh.

## 6. Two live bugs found by verifying

**The loading poster overflowed its stage by 926px.** Measured 498×1500 inside
546×574. It read as the poster *tiling*, because the overflow was clipped by the
sections above and below. Cause: the `<img>` is a grid item, so `min-height: auto`
floored it at intrinsic height and silently beat `max-height: 100%`. `max-width`
alone still left 623px; **`min-height: 0`** is the line that fixes it → 421×526.
Pre-existing since launch and invisible only because every poster was a flat
drawing.

**A CSP violation on every live page load.** Not our HTML — Cloudflare's edge
injects a 921-char inline script, and its hash is not in the allowlist. Confirmed
by reading the live DOM: four scripts, the third absent from the delivered HTML.

> ❌ **This section originally attributed the injection to Web Analytics'
> "Automatic Setup" and prescribed a dashboard toggle. That was wrong** — see §9,
> corrected 2026-08-06. It is Bot Fight Mode's JavaScript Detections. The error was
> inferring the script's identity from which Cloudflare product we already knew was
> enabled, rather than reading its 921 characters, which name themselves in the
> clear (`/cdn-cgi/challenge-platform/scripts/jsd/main.js`).

## 8. The smoke test failed its own first deploy

Worth recording because it is the exact failure mode this repo keeps writing
about, committed by the check that was meant to prevent it.

The deploy succeeded — migrations, CMS worker, viewer worker and the health check
all shipped — and then the new smoke test turned the run red with
`HTTP 403 fetching the model`.

**Free-plan Bot Fight Mode intermittently 403s datacenter traffic to
`wear-run.help` hosts, and this is already documented in HARDENING-LOG.md**, where
it forced the `cms.wear-run.help` API cutover to be rolled back within the hour. A
GitHub runner is datacenter traffic. So a gate shipped with a known, pre-recorded
false-negative source pointed straight at CI.

It was also downloading the whole **37.7 MB** model on every deploy *and* every
15-minute uptime run — roughly **3.6 GB of R2 egress a day** against a $5/month
cap, to read a number that is in the response headers.

Both fixed in `8c6e27e`: `HEAD` (with a 1-byte ranged GET as fallback), and a 403
now warns that the URL could not be verified from here rather than failing. Every
payload assertion still fails hard — those are what actually catch a product with
no model. All five negative controls re-run and still fail correctly.

**The lesson generalises:** before pointing a new gate at CI, check whether the
repo has already recorded a reason it will fire spuriously. A gate the owner
learns to override is worse than no gate — this repo says exactly that about
`findCrushedArtwork`, and I did not apply it to my own check.

## 9. Closing out the three open items (later the same day)

### Run C adopted — and two stale copies of the old preset found

`balanced` moved from `--simplify-error 0.0005` to `0.001` in
`packages/shared/src/shrink.ts`. Cheaper than the code comment implies:
`shrinkFlagsFor` is called in the *Worker* (`apps/shrink/src/index.ts:219`) and the
flags travel to the container in the job message, so this is a Worker deploy with
**no Docker rebuild**.

A new test pins the number. Every other assertion in `shrink.test.ts` is *relative*
— fidelity ≤ balanced, uv weight never below balanced — which is the right shape for
an invariant and is why the suite survived `small` being deleted without a rewrite.
But a relative assertion cannot pin a value: **0.001 and 0.005 both satisfy every one
of them**, and 0.005 renders the wordmark destroyed. So there is now exactly one
absolute assertion, carrying the measurement and the path to the contact sheet.

Grepping for the old value then found two live copies that had silently drifted:

| file | what was wrong |
|---|---|
| `scripts/bisect-artwork.mjs` | `DETAIL_FLAGS.balanced` still 0.0005 — a bisect of a *new* upload would have reproduced a preset that no longer ships |
| `scripts/sweep-size-vs-artwork.mjs` | run A labelled "balanced (shipped)", run E "small (shipped)" — neither true; the contact sheet is what the next investigation reads first |

The bisect script's duplication is *deliberate* and documented (it must be editable
to reproduce a job that already ran). That is still fine — but deliberate duplication
needs a dated note when the original moves, so the old value is now kept under
`balanced-pre-2026-08-05` rather than masquerading as current. `docs/RUNBOOK.md`'s
2026-07-28 calibration table got the same treatment: the measurements stand, the row
labels no longer claim to describe current presets.

Left alone deliberately: the `0.0005` in `pipeline.test.ts` is an arbitrary
arg-parsing value, not the preset, and the sweep tables in the docs above are
historical records of what was measured.

### The CSP builder got its first tests, and analytics turned out to be dead

`apps/viewer/scripts/gen-headers.mjs` had **no test of any kind**, despite having
caused two production incidents on its own (the missing self-hosted decoder location,
and the missing `blob:` that tripped every meshopt-compressed garment). It could not
be tested as written: it reads `dist/` and writes `_headers` at import time.

Policy construction is now a pure `buildCsp()` in `scripts/csp.mjs`, with 10 tests.
The refactor was verified by building with the production `VITE_API_BASE_URL` and
diffing the generated policy against the one live in production — **byte-identical**.

One test is subtler than it looks. Asserting "a `<script src>` adds no hash" using a
normal beacon tag would pass even with the regex's negative lookahead deleted, because
a src script's body is empty and the `!body` guard skips it anyway. So there is a
separate case with a src script that *has* a body — that one actually exercises the
lookahead.

**Then the diagnosis turned out to be wrong** (2026-08-06). Reading the injected
script instead of inferring it:

```
window.__CF$cv$params={r:'a26ba6e86e628a05',t:'MTc4NTk5NDI1MQ=='};
… a.src='/cdn-cgi/challenge-platform/scripts/jsd/main.js';
```

That is **Bot Fight Mode's JavaScript Detections**, a different Cloudflare product.
Web Analytics was never involved — the delivered HTML has zero matches for
`cloudflareinsights`, and a live load makes zero requests to it.

Two consequences, both material:

1. **The prescribed fix would not have worked.** Cloudflare documents that for Bot
   Fight Mode customers, JavaScript Detections is *"automatically enabled and cannot
   be disabled"*. Disabling Web Analytics Automatic Setup does nothing here.
2. **No hash can ever cover it.** The script embeds a per-request ray id and
   timestamp, so its sha256 changes on every load — three values measured inside a
   minute: `YQqe7Ux…`, `jgl9AA6h…`, `eXCOhXoR…`. The earlier note that pinning the
   hash "goes stale on every Cloudflare update" understated it by several orders of
   magnitude; it goes stale between two consecutive page views.

**How the error happened is the lesson.** Bot Fight Mode was *already documented in
this repo* as enabled and troublesome — it forced the `cms.wear-run.help` cutover
rollback and failed a deploy. The session knew Web Analytics was enabled, saw an
injected script, and matched it to the product it was already thinking about. The
921 characters name themselves in the clear. **Reading the artefact would have cost
less than the inference did** — which is this repo's own recurring lesson, arriving
this time as a misattribution rather than a missing test.

The beacon was still worth embedding: analytics genuinely were collecting nothing.
It is now a manual `<script src>` in `index.html`, verified to add **no** CSP hash
(the built policy is byte-identical to the previous one). That fixes analytics; it
does **not** fix the CSP violation, which needs a decision on Bot Fight Mode.

### Product specs

The best available source was checked first and came up empty: the raw 382 MB CLO
export names its fabrics `FABRIC 3` and `FABRIC 5`, CLO's generic defaults. It does
confirm the garment uses **exactly two** distinct fabrics, so any single composition
line describes the main body only.

Owner chose `garmentFit` = **"Race fit"**. Fabric and GSM were *not* recoverable, and
the owner asked for category research rather than leaving them blank — so
`fabricComposition` becomes **"80% recycled polyester / 20% elastane"** and `gsm`
stays **"160 GSM"** (already mid-range, and changing it to a different invented number
would add risk without adding accuracy).

> ⚠️ **These two are category-typical figures, not measurements of this garment.**
> Mainstream skinsuit main-body blends cluster at 77–80% polyester / 20–23% elastane;
> general cycling-fabric guidance puts elastane at 8–20% and weights at 80–180 GSM.
> They are owner-approved, not verified. Replace them when the mill spec arrives.

### The part worth recording: every green signal, and an unreachable file

Before the swap, the new model returned **`GET` 404** from
`media.wear-run.help` — a 28 KB Cloudflare error page — while **`HEAD` returned 200
with the correct `content-length`**. They land on different cache entries.

It is an R2 custom domain with a 30-day edge Cache Rule, and the cached 404 was
**25 hours old**, from a probe made before the file existed. The object was intact
in R2 throughout (`wrangler r2 object get` → all 28,271,780 bytes) and the same URL
with `?v=1` served 200 instantly. One Custom Purge fixed it.

`artworkVerdict: ok`, the filesize, the alphaMode census, the pipeline report and a
`HEAD` were **all green while the file was unreachable**. Pointing `glbAsset` at it
on those signals would have put a 404 on the live page — the same shape of failure
as the artwork bug, one layer out: the checks agreed with each other and none of
them was the thing the visitor experiences. `smoke-viewer-payload.mjs` uses `HEAD`
by design (R2 egress against the $5/month cap), so it would not have caught it
either.

After the purge: bare `GET` 200, model loads in a real browser with all five
variants, smoke test green.
