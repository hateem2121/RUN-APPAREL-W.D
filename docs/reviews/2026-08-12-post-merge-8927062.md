## Step 1 — `/render`: the guard, its mirror, and its headers

### 1.1 ✓ The e2e mirror has NOT drifted

`apps/viewer/e2e/serve.mjs:236-246` hand-reimplements `isAllowedRenderModel`
rather than importing it. Compared line by line against
`apps/viewer/worker/renderGuard.ts:30-43`: **logically identical** — same
falsy-guard, same `new URL(rawModel, pageOrigin)` in a try/catch, same
`url.origin === pageOrigin` short-circuit, same
`url.protocol === 'https:' && /(^|\.)wear-run\.help$/.test(url.hostname)`.

No finding. The drift risk is real but has not materialised.

### 1.2 ✓ The regex resists suffix bypass, and is properly tested

`/(^|\.)wear-run\.help$/` against `url.hostname` — anchored both ends, dot
escaped. `renderGuard.test.ts` covers `wear-run.help.evil.com`,
`evilwear-run.help`, plain `http:`, `//evil.com/x.glb`, bare `https://`, a
malformed host, `null` and `''`. That is a genuinely adversarial test file.
Spent no further effort here.

### 1.3 ✓ `/render` DOES receive the CSP — hypothesis disproven

I expected `/render` (one path segment, brand new) to fall outside the header
rules, which were shaped for two-segment garment URLs. Wrong: `csp.mjs:202`
attaches every security header to `/*`, which matches everything.

Confirmed live, `GET https://viewer.wear-run.help/render?model=…` → 200 carries
`content-security-policy`, `strict-transport-security`, `permissions-policy`,
`referrer-policy`, `x-content-type-options: nosniff`.

### 1.4 **L** — the Worker-built 400 ships with NO security headers

**Measured live, 2026-08-12.** Same route, two outcomes:

| Header | `/render` 200 (asset-served) | `/render` 400 (Worker-built) |
|---|---|---|
| `content-security-policy` | present | **absent** |
| `strict-transport-security` | present | **absent** |
| `x-content-type-options` | present | **absent** |
| `referrer-policy` | present | **absent** |
| `permissions-policy` | present | **absent** |

Cause: `worker/index.ts:286` returns `new Response('The "model" parameter…',
{status: 400})` — constructed from scratch, so it never passes through the static
asset handler that applies `_headers`. `apps/viewer/CLAUDE.md` measured that
headers *survive* `env.ASSETS.fetch()`; a from-scratch Response never enters that
path, which the measurement did not cover.

**Impact today: low.** The body is a fixed constant with no caller-controlled
input, and the runtime set `content-type: text/plain;charset=UTF-8` correctly, so
there is no injection or sniffing vector. The real cost is the missing HSTS on
that response and the precedent.

**The durable risk is the generalisation:** *any* response this Worker builds
itself bypasses `_headers`. Today that is one plain-text 400. The day someone
adds a Worker-rendered HTML error or interstitial, it ships with no CSP and
nothing in the suite says so.

**Fixture inversion worth recording:** `serve.mjs:254` sets `GLOBAL_HEADERS` on
every response *before* the `/render` check, so the e2e fixture's 400 **does**
carry the headers. A test asserting "the 400 has a CSP" would pass locally and be
false in production.

*Suggested fix (not applied): give the Worker one `securityHeaders()` helper for
self-built responses, or return the 400 through the asset pipeline. Cheap.*

### 1.5 ✓ Zone-wide trust adds no R2 egress exposure — hypothesis disproven

I flagged in the plan that a public unauthenticated `/render` might amplify R2
egress against the $5/month cap. It does not. `media.wear-run.help` is already a
public host — it has to be, because the browser fetches models from it directly,
and the live CSP confirms it (`img-src`/`connect-src` both allow
`https://*.wear-run.help`). Anyone wanting to burn egress can `GET` the object
directly; routing through `/render` adds a page load and no amplification.

Deliberately did **not** fetch a model to test this — per root `CLAUDE.md`, a
`GET` on a production model is ~37.7 MB against a $5/month cap.

Residual, accepted: `/render` will load any GLB on any `*.wear-run.help`
subdomain. Exploiting it requires already controlling a subdomain of the zone,
at which point this is not the weakest link.

### Step 1 verdict

One low-severity finding (1.4), two hypotheses of mine disproven by measurement
(1.3, 1.5), two clean checks (1.1, 1.2). **The renderGuard code itself is sound**
— the brief's worry about the regex was unfounded, and the mirror is in sync. The
only real gap is at the seam the guard hands off to: the rejection response.

Side benefit: 1.3/1.4 close an open item in `apps/viewer/CLAUDE.md`
("Still not re-checked against the live edge; do that once after the first
deploy"). Now checked. Headers confirmed present on the live edge for

### 2.4 ✓ QR slug permanence holds

untouched. The rule holds.

### 2.5 ✓ Blank-slug state is defended in depth

## Step 3 — poster capture: is the right colour in the photo?

`26ed54b`, `5c9d6e9`. I argued in the plan this should outrank the CSP item. It
was worth checking; all three concerns turn out to be explicitly handled.

### 3.1 ✓ Stale-readiness race — already found and closed

`__renderSetVariant` (`RenderPage.tsx:250`) calls `setRenderReady(false)`
**first, synchronously**, before touching the model, so a caller that already
observed `true` for the previous colour cannot read it for the new one. Credited
in the source to "task 14 review, finding 1" — found before I got here.

### 3.2 ✓ Unknown variant fails loudly, never silently

`applyTarget` (`RenderPage.tsx:171-185`) checks `mv.availableVariants` and
**returns without ever setting ready** when the requested variant is absent. The
comment cites the exact CLAUDE.md principle: a photo of the default variant
mislabelled as another colour is worse than no photo. The capture loop then times
out and records a failure (`index.ts:884-891`) rather than uploading.

### 3.3 ✓ Posters are keyed by slug, not by loop index

`posters.ts:78` builds targets `{slug, variantId}`; `index.ts:861` resolves
`freshRows.find((r) => r.slug === target.slug)`. If the row is gone, it pushes a
failure rather than writing to the wrong row (`index.ts:862-871`). It also
**re-reads product state immediately before each write** so a multi-minute loop
cannot revert an owner edit made partway through — credited to "task 14 review,
finding 2". One PATCH per capture, so a crash keeps what succeeded.

### 3.4 **L** — nothing verifies the captured pixels show the requested colour

The settle is the repo's known-weak one — `jumpCameraToGoal()` plus two chained
rAFs, copied deliberately from `render.ts`, which root `CLAUDE.md` describes as
*"best-effort rather than a convergence check."*

The guards above prevent the **known-bad** cases (variant absent, row renamed,
context lost). What is not covered: `variantName` is set, the variant genuinely
exists, but the new variant's textures have not finished uploading to the GPU
when the second rAF fires. That paints the previous colour's materials, signals
ready, and uploads a correct-looking poster under the wrong colour name. Every
gate passes.

I could not demonstrate this — it needs a real multi-colour garment, and per
CLAUDE.md only a rendered crop could settle it. Recording it as the residual
rather than a defect. Two things bound the risk: the robot writes drafts only, so
a human sees the posters in the admin before publish; and 3.1's ready-reset means
the swap gets at least a full frame.

*Cheap mitigation if you ever want it: the pipeline already computes `hexSwatch`
per colourway. Comparing the captured PNG's mean colour against it would catch a
wrong-variant capture automatically. That is the "look at the output" check this
path currently lacks.*

### Step 3 verdict

Better than I expected when I argued for promoting it. The promotion was still
right — this is where a silent customer-visible error would live — but the work
had already been reviewed once and the obvious races closed. One residual (3.4).

# Update — finding 3.4 addressed 2026-08-12

Warning only, as scoped. The capture path is unchanged: every poster is still
taken, uploaded and linked exactly as before.

**The mechanism changed after reading the code, and the reason matters.** The
plan proposed comparing each poster's mean colour against the colourway's
`hexSwatch`. That is not reachable from where the capture runs — `index.ts`
states at the screenshot call that **Workers cannot run sharp** (it is why
posters ship as PNG rather than WebP), and `page.evaluate` is deliberately used
in string form because the shrink tsconfig carries no DOM lib. Measuring mean
colour would have meant putting a pure-JS PNG decoder into the path that
photographs every garment, in order to emit a *warning*. Wrong trade.

**Detect by identity instead.** The failure is "the previous colour's frame is
photographed under the new colour's name" — which is two colourways producing a
**byte-identical PNG**. That is the bug stated exactly, needs no decoding, and is
meaningful in this repo specifically because byte-identical renders are the norm
for identical input (root `CLAUDE.md` records four PNGs at `sha256 294291db…`
while calibrating the field-of-view floor).

`hexSwatch` still earns its place, as the qualifier rather than the measurement:

| Situation | Reported as |
|---|---|
| Identical image, swatches genuinely differ | "the file says they are different colours — one is almost certainly wrong" |
| Identical image, same swatch | hedged; two colours may truly look alike |
| Identical image, either swatch missing | hedged; absence is not evidence |

That last row is deliberate. Rows the owner typed by hand carry no swatch, and a
false alarm on a hand-built garment teaches them to ignore the warning — worse
than not having it.

**Shipped:** `frameDigest` and `checkCapturedFrame` in `apps/shrink/src/posters.ts`
(pure, following the planPosters split that exists because the capture shell
itself cannot be tested), wired into `capturePosters`, reported as a `⚠️` line
appended to the owner's report rather than folded into `failures` — these
captures succeeded, and calling them failures would tell the owner to redo work
that may be correct. 10 new tests; `apps/shrink` 68 → 78.

**What this still does not do.** It cannot detect a wrong colour that happens to
differ from every other frame — a partial texture upload that lands somewhere
between two colours would pass. Only a human looking at the poster settles that,
which was the original finding's point. This narrows the gap to "wrong AND
visibly distinct from its neighbours" rather than closing it.
