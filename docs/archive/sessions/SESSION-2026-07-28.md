### How to prove a pnpm patch is actually live (worth keeping)

The F1 fix lives in a pnpm patch, applied at install time and baked into a
Next.js **client** chunk at build time. Nothing in CI or the Cloudflare dashboard
tells you whether it survived. But client chunks are public and unauthenticated:

```bash
curl -s https://cms.wear-run.help/admin/login | grep -o '/_next/static/chunks/[A-Za-z0-9._/-]*\.js'
# download them, then grep for the patched code
```

The deployed bundle contains `m=()=>` — the endpoint rebuilt per call — and not
the frozen `endpoint = ` string. The same chunk hash appears in a local
`pnpm build`, so the local build can be checked identically before deploying.

**Do not infer deployment state from CI logs or `modified_on` timestamps.** That
error is what produced the false "pipeline is not operational" claim on
2026-07-26, and a variant of it appears again in Part 3 below.

## Part 2 — the two new defects

### 5. `APIError` was fixed in one hook and left broken in six others

`fd0ecc6` converted `RawUploads.beforeChange`. It did not touch `rawRules.ts` or
`mediaRules.ts`, which still threw plain `new Error()` from `beforeValidate` —
so **every routine rejection an operator actually hits** (wrong file type,
`.zprj`, over the size cap, unsafe filename) still rendered as *"Something went
wrong."* The one path that had been fixed was the rare one.

**Lesson:** when you fix an error-surfacing bug, grep the repo for the pattern.
Fixing the instance you tripped over is not fixing the bug.

### 6. The shrink output could not fit, so the pipeline could never complete

`apps/shrink/container/server.ts` hardcoded `--simplify 0.05`, which after the
2026-07-27 logo fix inherited `lockBorder: true` + `error: 0.0001`. That exact
combination was **measured the day before at 58.3 MB** on the real garment —
against `GLB_HARD_MAX_BYTES = 40 MB` in `mediaRules`. The first end-to-end run
was arithmetically guaranteed to fail at the last step, retry twice, and
dead-letter. The measurement to prove it was already in the previous session log;
nobody had compared it against the cap.

Two non-obvious things behind it:

**`lockBorder` was the wrong instrument.** glTF-Transform documents it for
"adjacent 'chunks' of a large mesh (e.g. terrain) [that] share a border". It
stopped the logo tearing only as a side effect of freezing *every* open
boundary — necklines, cuffs, hems, every UV island — which is what took 850k
triangles to 6.0M. meshoptimizer ships the designed tool and names this exact
case in its own README: `simplifyWithAttributes` improves "texture deformation
(by using texture coordinates)". With UV error inside the budget, `LockBorder`
is unnecessary and the mesh interior is free to collapse.

**`--simplify` is a target, not a promise.** Once the error budget binds,
lowering the ratio does *nothing at all*. This invalidated the standing advice in
both READMEs ("start at 0.05 and lower it to hit the 8 MB guideline") and one of
the options in this session's own first draft plan. The knobs that move the
output are `--simplify-error` and `--uv-weight`.

## Calibration — the numbers behind the three Detail levels

Measured on a synthetic 243,602-triangle draped surface with a non-linear unwrap
and a hard-edged texture, running the real pipeline. Texture error is the
distance between the UV the decimated mesh interpolates at a point and the UV
that point should have. **Control (undecimated): 1.3e-6.**

| setting | triangles | size (meshopt) | mean err | p99 err |
|---|---|---|---|---|
| OLD `lockBorder`, err 0.0001 | 58,378 | 0.29 MB | 0.00001 | 0.00013 |
| OLD `lockBorder`, err 0.001 | 12,180 | 0.07 MB | 0.00006 | 0.00073 |
| **fidelity** (uv 2, err 0.0002) | 20,421 | 0.11 MB | 0.00003 | 0.00036 |
| **balanced** (uv 1, err 0.0005) | 12,180 | 0.07 MB | 0.00005 | 0.00054 |
| **small** (uv 0.5, err 0.002) | 4,872 | 0.04 MB | 0.00013 | 0.00161 |

- At **equal size**, texture-aware beats position-only: `balanced` and OLD-0.001
  both land on 12,180 triangles, but p99 error is 0.00054 vs 0.00073.
- The **size win is the larger effect**: `fidelity` holds p99 within 3x of the
  old safest setting using **2.9x fewer triangles**; `balanced` uses 4.8x fewer.
- **Caveat:** this surface is one smooth UV patch. A real CLO unwrap has many
  islands and `lockBorder` freezes every island edge, so its real-world cost
  should be *worse* than measured here. Directional until re-measured on a real
  garment.

## Method lessons

**A test harness without a control can only produce confident nonsense.** The
first run of the calibration above printed a full, plausible table. It was
wrong — positions quantized a hair below zero made `u ** 1.3` return NaN, and
UVs outside `[0,1]` made glTF-Transform's quantize step skip TEXCOORD_0
silently. Adding one row that measures the *undecimated* mesh (which must read
~0) exposed both immediately.

**Pick the fixture to match the phenomenon.** The first unit test for
attribute-aware simplification used a flat grid with **linear** UVs, where the
weighting provably cannot matter: a coarser triangulation interpolates to
identical UVs. Every weight from 0 to 100 gave the same 20 triangles. Real
unwraps are non-linear; the fixture had to be too.

**Cheap platform queries beat expensive reasoning.** A D1 `SELECT` found
`media.id = 7` named `Maroon` with `mimeType image/png` — a file with no
extension whose type macOS supplied from the UTI. That single row explained the
unexplained "cycling all colours" filename in one step, after a long source
trace had failed to.
