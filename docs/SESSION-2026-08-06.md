# Session 2026-08-06 — the agent tooling audit, and closing the legibility gap

**In plain words:** A diary of one work session: checking the AI tools and closing old issues.

Two halves. The morning was an audit of the AI-agent tooling around this repo
(skills, MCP servers, hooks, plugins). The afternoon acted on it, and in doing so
closed the one hole `CLAUDE.md` had been naming since 2026-08-05: **nothing
measured whether the printed letters survived.**

The useful part of this document is not the list of changes. It is the four things
that turned out to be false, each of which had been written down as fact.

---

## 1. Four beliefs that were wrong

### "CI's rasteriser will produce different numbers from a developer Mac"

Stated in `ci.yml` as the reason the `artwork` job was observe-only rather than a
deploy gate — the `8c6e27e` lesson applied pre-emptively. **Measured and false.**

| | fidelity | balanced | control |
|---|---|---|---|
| macOS, local | 1.650% | 3.070% | 9.370% |
| CI ×3 runs, 2 runner images | 1.650% | 3.070% | 9.370% |

Identical to three decimal places. The reason is in the eval's own header and was
never followed through: there is **no golden image**. Every comparison is between
two renders taken by the same browser in the same run, so the rasteriser appears on
both sides of the subtraction and cancels. Decimation is deterministic.

The job now gates the deploy, with the ceiling unchanged — the CI numbers *are* the
numbers it was calibrated against.

### "The sweep remains the authority on a real garment"

Stated in `CLAUDE.md`. **`sweep-size-vs-artwork.mjs` imports no renderer.** It
measures file size, `artworkAtRisk`, `findArtworkAlphaProblems` and the alpha
census. Its own recorded output (`output/sweep/sweep.json`, 2026-08-05) reports
`wouldShip: true` for **all six runs, including run F at `--simplify-error 0.005`**
— the run the same document says rendered the wordmark illegible.

The authority was never the sweep. It was a human opening a contact sheet the sweep
did not produce. The sweep is still right for *where the size floor is*; it was
never evidence about letters.

### "claude-mem is unused"

The audit reported it as an unproven tool holding 444 MB. It was worse than that:
**broken**, and its own log said so —

    Claude executable not found. Please either:
    1. Add "claude" to your system PATH, or
    2. Set CLAUDE_CODE_PATH in ~/.claude-mem/settings.json

Zero observations and zero session summaries in the entire database, across every
project, while a queue of 354 jobs retried every ~35 seconds and wrote 824 KB of
logs in a day. Removed on the owner's decision. It was fixable — a `claude` binary
exists inside the desktop app bundle — and that is recorded in
`~/.claude/backups/RESTORE-2026-08-06-tooling-plan.md` rather than lost.

### "Cleaning up the disabled plugins frees ~476 MB"

It freed about **2 MB**. The ten disabled plugins were tiny; 444 MB of the 446 MB
came from claude-mem alone. Disk was never the argument for that cleanup —
accumulation was, the same pattern that had produced 57 disabled skills nobody had
decided to remove.

## 2. The legibility gap, closed for N001

`pnpm eval:artwork:real` runs the synthetic eval's method on the actual 382 MB CLO
export, monthly, via `.github/workflows/artwork-real.yml`.

The baseline is **the full pipeline minus decimation** — same textures, same alpha
resolution, same meshopt, `--simplify` omitted. Rendering the raw file directly
would measure texture compression and decimation together and blame whichever you
already suspected.

Calibrated 2026-08-06, and reproducible to three decimal places across three runs:

| preset | changed | |
|---|---|---|
| `fidelity` | 0.980% | shipped, strictest |
| `balanced` | 2.990% | shipped |
| `--simplify-error 0.005` | 5.770% | sweep run F |
| `--uv-weight 0` | 5.810% | negative control |
| **ceiling** | **4.200%** | 1.40× above shipped, 1.37× below both failures |

Run F was confirmed by eye on the contact sheet: "THE EXTRA MILE" breaks apart and
the RUN arrow logo mangles. **That is the file the three blocking gates wave
through.** There is now a number that stops it.

Margins are tighter than the synthetic eval's (1.63× / 1.87×) and that is inherent:
this crop necessarily contains fabric and seams, and decimation legitimately moves
those. Separation is 1.93× rather than the fixture's 3.05×.

### The framing nearly made it useless

The first version used render.ts's own `crop-chest` view, because the name says
chest. On N001 it frames the torso and hips **with the wordmark clipped off the top
edge**; `crop-back` shows a zipper. Those angles were framed for a t-shirt, and
N001 is a skinsuit.

An eval calibrated on that crop would have measured how decimation moves *fabric*,
produced a plausible number, and gone green forever — the exact failure mode
`CLAUDE.md` opens with. It was caught by opening the PNG.

So the eval now **refuses to run if its camera is not aimed at the print**: it reads
the artwork primitives out of the built baseline, transforms them to world space,
takes the largest, and checks the configured target lands on it. A mis-aimed camera
does not error on its own — it just returns a number.

Two smaller measurements from the same hour: **model-viewer clamps orbit radius**
(0.445 m, 0.300 m and 0.180 m render pixel-identically, so `fieldOfView` is the only
zoom that works), and on the real garment `quantize` reports
`Skipping TEXCOORD_0; out of [0,1] range` — the real UVs fall outside the range the
synthetic fixture was deliberately built to stay inside.

## 3. The cached 404 became a control

On 2026-08-06 a model the shrink worker had just written returned `GET 404` from a
25-hour-old cached miss while `HEAD` returned 200 with the correct
`content-length`. Every automated signal was green. The defence was a paragraph in
`CLAUDE.md`.

`scripts/smoke-viewer-payload.mjs` now also does a **bare GET** — no HEAD, no Range,
no cache-buster — behind `SMOKE_BROWSER_GET=1`, set on the post-deploy path only and
deliberately **not** in `uptime.yml`: a cached 404 is created at publish time, so
polling for it every 15 minutes buys nothing and would cost ~3.6 GB of R2 egress a
day. The response body is cancelled once the status line arrives, so a real
browser-shaped GET costs about as much as the HEAD it complements.

Pinned by `apps/cms/src/endpoints/publicViewerSmoke.test.ts`. The middle test is the
point:

| scenario | result |
|---|---|
| HEAD 200 + GET 404, bare GET **on** | fails, names the Custom Purge fix |
| HEAD 200 + GET 404, bare GET **off** | **passes** — the blind spot, kept as a fact |
| HEAD 200 + GET 200 | passes |

## 5. Not verified

**`.github/workflows/artwork-real.yml` has never run.** The YAML parses,
`DEPLOY_ENABLED` is true and both Cloudflare secrets exist, but whether
`CLOUDFLARE_API_TOKEN` carries **R2 read** permission cannot be confirmed without a
382 MB download using a secret that is not available locally. If the first run fails
at the pull step, that is the cause, and the step says so.

One bug in it was caught before it shipped: the R2 key is
`cycling all colours.glb` — **with spaces** — not the hyphenated name the local
working copy uses. Recorded in
`docs/superpowers/specs/2026-08-05-n001-production-polish-design.md`, verified
2026-08-05.

**Trigger it by hand once from the Actions tab** rather than waiting for the 1st of
the month.

### ⚠️ And it will fail on its first scheduled run

Found immediately after shipping it, by re-verifying a stale comment. The ingest
bucket now carries an `expire-raw-uploads` lifecycle rule — **all prefixes, delete
after 14 days** — added at some point after 2026-07-28 and confirmed live on
2026-08-06:

    expire-raw-uploads             Expire objects after 14 days       enabled
    Default Multipart Abort Rule   Abort incomplete multipart uploads after 7 days

The N001 export was in the bucket on 2026-08-05, so it expires around **2026-08-19**.
The workflow's first schedule is **2026-09-01**. The file it needs will already be
gone.

**A raw CLO export is not a durable artifact in this system**, and the monthly eval
was built assuming it was. The rule itself is right — 350 MB files should not
accumulate against a $5/month budget. What is missing is a deliberate, exempt copy
of the one garment the eval measures.

The failure message now names this cause outright rather than reporting a bare
wrangler error. The fix is not applied: it needs either a second bucket with no
expiry, or a prefix-scoped rule, and that is an infrastructure decision rather than
a code change.
